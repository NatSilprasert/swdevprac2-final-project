# โครงงานที่ 2: ระบบขอเช่าอุปกรณ์ (Project 2: Equipment Rental System)

## รายละเอียด (Description)

พัฒนาส่วนติดต่อผู้ใช้ (frontend) ให้แก่ **ระบบขอเช่าอุปกรณ์ (Equipment Rental System)** สำหรับจัดการอุปกรณ์ที่เปิดให้ผู้ใช้เช่า และให้ผู้ใช้งานดูข้อมูลและขอเช่าอุปกรณ์ เช่น กล้องถ่ายรูป (Camera) โปรเจกเตอร์ (Projector) คอมพิวเตอร์โน้ตบุ๊ก (Notebook) หรืออุปกรณ์กีฬา (Sports Equipment) โดยระบบส่วนหลัง (backend) ในโครงงานนี้ให้บริการ RESTful API สำหรับการทำงานดังกล่าว

## ความสามารถของระบบ (Features)

### การจัดการผู้ใช้ (User Management)

- รองรับบทบาทผู้ใช้ (roles) 2 แบบ ได้แก่ ผู้ดูแลระบบ (admin) และสมาชิก (member) โดยใช้ค่า `admin` และ `member`
- ผู้ใช้สามารถลงทะเบียน (register) โดยระบุชื่อ (`name`), อีเมล (`email`), หมายเลขโทรศัพท์ (`tel`), บทบาท (`role`) และรหัสผ่าน (`password`)
- หลังลงทะเบียน ผู้ใช้สามารถเข้าสู่ระบบ (login) ด้วยอีเมล (email) และรหัสผ่าน (password)
- ระบบออกโทเคน JWT (JWT token) เป็นข้อมูลยืนยันตัวตนของผู้ใช้ (user credential) และรองรับการออกจากระบบ (logout)
- Backend API มีการควบคุมสิทธิ์ (access control) และเส้นทางที่ต้องยืนยันตัวตน (protected routes)

### การจัดการอุปกรณ์ (Equipment Management)

- ผู้ใช้ทุกคนสามารถดู (view) ข้อมูลอุปกรณ์ (Equipment) ได้
- หลังเข้าสู่ระบบ `admin` สามารถเพิ่ม (add) แก้ไข (update) ลบ (delete) และดู (view) ข้อมูลอุปกรณ์ (Equipment)
- อุปกรณ์ (Equipment) ที่สร้างใหม่ได้รับรหัส (`id`) สำหรับอ้างอิงในการแก้ไข (update) ลบ (delete) และสร้างคำขอเช่า (rental request)
- ข้อมูลอุปกรณ์ (Equipment) ประกอบด้วยชื่อ (name) หมวดหมู่ (category) คำอธิบาย (description) จำนวนอุปกรณ์ที่มี (available quantity) และอัตราค่าเช่าต่อชิ้นต่อวัน (rental rate per item per day)

### การจัดการคำขอเช่าอุปกรณ์ (Equipment Rental Management)

- หลังเข้าสู่ระบบ `member` สามารถสร้างคำขอเช่า (rental request) สำหรับอุปกรณ์ใดก็ได้ที่เปิดใช้งาน (active equipment) โดยระบุรหัสอุปกรณ์ (equipment id) และต้องผ่านเงื่อนไขการเช่า
- คำขอเช่า (Rental request) ประกอบด้วยจำนวนอุปกรณ์ (quantity) วันที่เริ่มเช่า (start date) และวันที่คืน (return date)
- การสร้างคำขอเช่า (rental request) เป็นการส่งคำขอ โดยยังไม่มีการเปลี่ยนจำนวนอุปกรณ์ในระบบทันที
- `member` สามารถดู (view) แก้ไข (edit) และลบ (delete) คำขอเช่า (rental request) ของตนเอง
- `admin` สามารถดู (view) แก้ไข (edit) และลบ (delete) คำขอเช่า (rental request) ของผู้ใช้ใดก็ได้

## เงื่อนไข (Conditions)

- วันที่เริ่มเช่า (start date) ต้องไม่ก่อนวันปัจจุบัน
- วันที่คืน (return date) ต้องไม่ก่อนวันที่เริ่มเช่า
- จำนวนอุปกรณ์ที่ขอเช่า (rental quantity) ต้องไม่เกินจำนวนอุปกรณ์ที่มี (available quantity)
- สามารถขอเช่าอุปกรณ์ (Equipment) เดียวกันได้สูงสุด **3 ชิ้นต่อคำขอเช่า (rental request)**
- ระยะเวลาเช่า (rental duration) ต้องไม่เกิน **7 วัน**

## API ที่มีให้ใช้งาน (Available APIs)

โค้ดมี **API สำหรับการทำงานของระบบ 14 endpoints** และ **endpoints สำหรับตรวจสอบระบบและเอกสาร 3 endpoints**

Base URL เริ่มต้นคือ `http://localhost:5000` (เปลี่ยน `5000` เป็นค่าที่กำหนดใน `PORT`)

### API สำหรับยืนยันตัวตน (Authentication APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| POST | `/api/v1/auth/register` | ทุกคน (Public) | ลงทะเบียนด้วย `name`, `email`, `tel`, `password` และ `role` ซึ่งไม่จำเป็นต้องระบุ (ค่าเริ่มต้นคือ `member` หรือเลือกเป็น `admin`) ส่งกลับข้อมูลผู้ใช้และ JWT |
| POST | `/api/v1/auth/login` | ทุกคน (Public) | เข้าสู่ระบบด้วย `email` และ `password` ส่งกลับข้อมูลผู้ใช้และ JWT |
| GET | `/api/v1/auth/me` | `member` หรือ `admin` | ดูข้อมูลผู้ใช้ที่ยืนยันตัวตนอยู่ในขณะนั้น |
| GET | `/api/v1/auth/logout` | `member` หรือ `admin` | ล้าง cookie ที่เก็บ token |

Protected APIs รับข้อมูลยืนยันตัวตนจาก header `Authorization: Bearer <token>` เท่านั้น การลงทะเบียนและเข้าสู่ระบบตั้งค่า cookie ชื่อ `token` ด้วย แต่ middleware ไม่อ่าน cookie นี้ การออกจากระบบล้าง cookie โดยไม่ได้เพิกถอน bearer token ที่ออกไปแล้ว

### API สำหรับอุปกรณ์ (Equipment APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| GET | `/api/v1/equipment` | ทุกคน (Public) | ดูรายการอุปกรณ์ที่เปิดใช้งาน โดยเรียงตามชื่อ |
| GET | `/api/v1/equipment/:id` | ทุกคน (Public) | ดูรายละเอียดอุปกรณ์ที่เปิดใช้งานหนึ่งรายการ |
| POST | `/api/v1/equipment` | `admin` | สร้างอุปกรณ์ด้วย `name`, `category`, `description`, `quantity` และ `rentalRate` |
| PUT | `/api/v1/equipment/:id` | `admin` | แก้ไขอุปกรณ์ที่เปิดใช้งานตามฟิลด์ที่ส่งมา |
| DELETE | `/api/v1/equipment/:id` | `admin` | ลบแบบ soft delete โดยตั้งค่า `isActive: false` |

ชื่ออุปกรณ์ต้องไม่ซ้ำ `quantity` เป็นจำนวนเต็มไม่น้อยกว่า `0` และ `rentalRate` ไม่น้อยกว่า `0` โดยกำหนดให้เป็นค่าเช่าต่อชิ้นต่อวัน ปัจจุบันไม่มี API คำนวณยอดค่าเช่าหรือรับชำระเงิน และไม่รองรับ query parameters สำหรับค้นหา กรองข้อมูล หรือแบ่งหน้า

### API สำหรับคำขอเช่า (Rental Request APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| GET | `/api/v1/rentals` | `member` หรือ `admin` | `member` ได้รับเฉพาะคำขอของตนเอง ส่วน `admin` ได้รับทั้งหมด โดยเรียงตามวันที่เริ่มเช่าและวันที่สร้าง |
| GET | `/api/v1/rentals/:id` | เจ้าของคำขอ หรือ `admin` | ดูคำขอพร้อมรายละเอียดผู้ใช้และอุปกรณ์ที่เกี่ยวข้อง |
| POST | `/api/v1/rentals` | เฉพาะ `member` | สร้างคำขอด้วย `equipment`, `quantity`, `startDate` และ `returnDate` |
| PUT | `/api/v1/rentals/:id` | เจ้าของคำขอ หรือ `admin` | แก้ไขฟิลด์ที่ส่งมา ได้แก่ `equipment`, `quantity`, `startDate`, `returnDate` |
| DELETE | `/api/v1/rentals/:id` | เจ้าของคำขอ หรือ `admin` | ลบคำขอออกจากฐานข้อมูลอย่างถาวร |

ตัวอย่างคำขอสำหรับสร้างคำขอเช่า (Rental Request Example):

```json
{
  "equipment": "<equipment MongoDB ID>",
  "quantity": 2,
  "startDate": "2026-12-01",
  "returnDate": "2026-12-08"
}
```

เปลี่ยนวันที่ในตัวอย่างให้เป็นวันปัจจุบันหรืออนาคตเมื่อลองใช้งานจริง

เงื่อนไขที่ตรวจสอบในโค้ด (Implemented Validation Rules):

- วันที่ใช้รูปแบบ `YYYY-MM-DD` และต้องเป็นวันที่มีอยู่จริงในปฏิทิน โดยใช้ **UTC** ในการกำหนดวันปัจจุบัน เช่นเดียวกับ PJ01
- วันที่เริ่มเช่าต้องไม่ก่อนวันปัจจุบัน และวันที่คืนต้องไม่ก่อนวันเริ่มเช่า
- ระยะเวลาเช่าคำนวณจาก **วันที่คืนลบวันที่เริ่มเช่า** ต้องไม่เกิน 7 วัน เช่น 1 ธันวาคมถึง 8 ธันวาคมถือเป็น 7 วัน และสามารถเริ่มเช่าและคืนวันเดียวกันได้
- `quantity` ต้องเป็นตัวเลขจำนวนเต็มตั้งแต่ **1–3** และไม่เกินจำนวนอุปกรณ์ที่มีในขณะสร้างหรือแก้ไขคำขอ
- ตรวจสอบเงื่อนไขทั้งหมดทั้งการสร้างและแก้ไข โดยฟิลด์ที่ไม่ส่งมาในการแก้ไขคงค่าเดิมไว้ ส่วนค่า `null` ไม่ถือว่าเป็นการละเว้นฟิลด์
- อุปกรณ์ที่อ้างอิงต้องมีอยู่และเปิดใช้งาน หากถูก soft delete คำขอเดิมยังดูหรือลบได้ แต่การแก้ไขต้องเปลี่ยนไปอ้างอิงอุปกรณ์ที่เปิดใช้งาน
- เจ้าของคำขอมาจากผู้ใช้ที่ยืนยันตัวตน ไม่รับค่า `user` จาก request body และไม่อนุญาตให้แก้ไขเจ้าของคำขอ
- การสร้าง แก้ไข และลบคำขอไม่เปลี่ยนจำนวนอุปกรณ์ แต่ละคำขอตรวจสอบจำนวนแยกกันโดยไม่จองหรือตัดสต็อก และไม่มีข้อห้ามเรื่องวันที่ซ้อนกัน
- ไม่มีขั้นตอนอนุมัติ ปฏิเสธคำขอ ตัดสต็อก หรือรับคืนอุปกรณ์ในข้อกำหนดปัจจุบัน

| GET | `/health` | ทุกคน (Public) | แสดงสถานะ application, timestamp และ environment โดยไม่ตรวจสอบการเชื่อมต่อฐานข้อมูล |

### รูปแบบการตอบกลับ (Response Format)

การสร้างข้อมูลสำเร็จส่งกลับ `201` ส่วนการทำงานอื่นของ application ที่สำเร็จส่งกลับ `200` โดยทั่วไป response ใช้ `{ success, data }` และเพิ่ม `count` สำหรับรายการ ส่วน JWT ส่งกลับใน `data.token`

ข้อผิดพลาดใช้ `{ success: false, error }` การผิดเงื่อนไขคำขอเช่าส่งกลับ `400` การไม่ยืนยันตัวตนส่งกลับ `401` การไม่มีสิทธิ์ส่งกลับ `403` และการไม่พบข้อมูลส่งกลับ `404` ส่วนข้อผิดพลาดจากฐานข้อมูลที่ไม่ได้จัดการเฉพาะ เช่น Mongoose validation/cast error ส่งต่อไป global error handler และใช้ `500` เป็นค่าเริ่มต้นตามรูปแบบ PJ01

## กลไกการยืนยันตัวตน (Authentication)

Authentication controller อยู่ใน [controllers/auth.js](controllers/auth.js) ส่วน methods สำหรับ password และ JWT อยู่ใน [models/User.js](models/User.js)

### การลงทะเบียน เข้าสู่ระบบ และสร้างโทเคน (Registration, Login, and Token Generation)

1. `POST /api/v1/auth/register` สร้างผู้ใช้ โดย user model hash password ด้วย bcrypt ก่อนบันทึก และส่งกลับ HTTP `201`
2. `POST /api/v1/auth/login` ตรวจสอบ email และเปรียบเทียบ password กับ bcrypt hash แล้วส่งกลับ HTTP `200`
3. ทั้งสอง endpoint เรียก `sendTokenResponse()` สร้าง JWT ซึ่งมี ID ของผู้ใช้ ลงลายเซ็นด้วย `JWT_SECRET` และกำหนดอายุผ่าน `JWT_EXPIRE`
4. JWT เดียวกันส่งกลับใน `data.token` และ cookie ชื่อ `token`

ตัวอย่างการตอบกลับเมื่อยืนยันตัวตนสำเร็จ (Successful Authentication Response):

```json
{
  "success": true,
  "data": {
    "id": "507f1f77bcf86cd799439011",
    "name": "Example Member",
    "email": "member@example.com",
    "role": "member",
    "token": "<JWT>"
  }
}
```

### การยืนยันตัวตนด้วยโทเคน Bearer (Bearer Token Authentication)

Client แนบ token กับทุก request ที่ต้องยืนยันตัวตน:

```http
GET /api/v1/rentals HTTP/1.1
Authorization: Bearer <JWT>
```

Middleware `protect` ใน [middleware/auth.js](middleware/auth.js) อ่าน bearer header ตรวจสอบลายเซ็นและอายุ JWT แล้วค้นหาผู้ใช้ตาม ID หากไม่มี token, token ใช้ไม่ได้ หรือไม่มีผู้ใช้นั้น จะส่งกลับ `401` เมื่อผ่านการตรวจสอบ middleware จะเก็บผู้ใช้ใน `req.user`

Middleware `authorize` ตรวจสอบ role ส่วน controller ตรวจสอบความเป็นเจ้าของคำขอ หากไม่มีสิทธิ์จะส่งกลับ `403`

### คุกกี้และโทเคน Bearer (Cookie and Bearer Token)

| ตัวเลือกคุกกี้ (Cookie Option) | การทำงาน (Behavior) |
|---|---|
| `httpOnly` | JavaScript ใน browser อ่าน cookie ผ่าน `document.cookie` ไม่ได้ |
| `expires` | คำนวณจาก `JWT_COOKIE_EXPIRE` ซึ่งมีหน่วยเป็นวัน |
| `secure` | เปิดใช้เมื่อ `NODE_ENV` เป็น `production` |

`JWT_EXPIRE` กำหนดอายุ JWT ส่วน `JWT_COOKIE_EXPIRE` กำหนดอายุ cookie ซึ่งเป็นค่าที่แยกกัน การส่งเฉพาะ cookie ไม่สามารถยืนยันตัวตนได้ เพราะ `protect` ไม่อ่าน `req.cookies.token`

| ข้อมูลยืนยันตัวตน (Credentials) | ผลการยืนยันตัวตน (Authentication Result) |
|---|---|
| Bearer JWT ที่ถูกต้อง | ยอมรับหากยังมีผู้ใช้อ้างอิงอยู่ โดยต้องผ่านการตรวจสอบ role และเจ้าของข้อมูลด้วย |
| เฉพาะ token cookie | ปฏิเสธด้วย `401` |
| Bearer JWT และ token cookie | ตรวจสอบเฉพาะ bearer JWT |
| Bearer JWT หมดอายุหรือไม่ถูกต้อง พร้อม cookie ที่ถูกต้อง | ปฏิเสธด้วย `401` โดยไม่ใช้ cookie เป็นทางเลือกสำรอง |

### การใช้การยืนยันตัวตนใน Swagger (Swagger Authorization)

ที่ `/api-docs` ให้คัดลอก `data.token` หลังลงทะเบียนหรือเข้าสู่ระบบ คลิก **Authorize** แล้ววาง JWT โดยไม่เติม `Bearer ` เพราะ Swagger เติมให้ใน header ไม่มีตัวเลือก `cookieAuth`

### การออกจากระบบและการหมดอายุของโทเคน (Logout and Token Expiration)

`GET /api/v1/auth/logout` ต้องใช้ bearer token ที่ถูกต้อง โดย controller แทนค่า cookie ด้วย `none` และกำหนดให้หมดอายุในอีก 10 วินาที การออกจากระบบไม่เพิกถอน JWT ดังนั้น frontend ต้องลบ bearer token ที่เก็บไว้ และผู้ใช้ Swagger ต้องล้าง authorization แยกต่างหาก Backend ไม่มี refresh-token endpoint เมื่อ token หมดอายุต้องเข้าสู่ระบบใหม่

## การตั้งค่าและตรวจสอบ (Setup and Verification)

ติดตั้ง dependencies ด้วย `npm ci` จาก directory `PJ02-EquipmentRent` และตั้งค่า `MONGO_URI` ใน [config/config.env](config/config.env) ซึ่งเว้นว่างไว้ตามที่กำหนด จากนั้นใช้ `npm run dev` หรือ `npm start` และกำหนด `JWT_SECRET` ของตนเองก่อน deploy

เมื่อ `MONGO_URI` ว่าง server ยังเปิด welcome endpoint, health endpoint และ Swagger UI ได้ แต่ API ที่ใช้ฐานข้อมูลต้องกำหนด connection string ก่อน หากรัน PJ01 พร้อมกันให้ตั้ง `PORT` ของอีกโครงงานต่างกัน

`npm test` ตรวจ syntax ของ entry point ตาม PJ01
